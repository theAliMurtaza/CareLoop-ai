# CareLoop deployment handover

Prepared for the existing **D:\CareLoop** repository on 22 November 2026. You create the hosting accounts, enter their credentials, review charges, and click Deploy. No public service, GitHub push, or paid resource has been created by these preparation scripts.

This remains a **synthetic-data demonstration**. Keep `SYNTHETIC_DATA_ONLY=true`; seeded ranges await your source verification. Start in offline mode, which needs no model key. Reminders currently use the CareLoop inbox.

## 2. Cloud configuration has been prepared

Run from PowerShell:

```powershell
cd D:\CareLoop\build
npm run setup:deployment
notepad .\deployment\.env
```

The command needs Node 24 but no dependency installation. It is safe to rerun: it preserves the separately generated cloud encryption/signing keys and does not edit the working local Compose `.env` files.

In `build/deployment/.env`, fill values as each platform gives them to you:

| Input | Where to obtain it |
| --- | --- |
| `DATABASE_URL` | Neon Connect panel, PostgreSQL URI with TLS; Supabase alternative below |
| `AI_URL` | Render AI service's HTTPS URL |
| `API_URL` | Render API service's HTTPS URL |
| `FRONTEND_URL` | Stable Vercel production URL, not a changing preview URL |
| `N8N_URL` | Hosted n8n HTTPS URL, if deploying automation |
| `AI_MODE` | Leave `offline` initially |
| `LLM_PROVIDER`, `LLM_MODEL`, selected key | Optional live-provider configuration after offline checks pass |

Use origins such as `https://your-service.onrender.com`, without paths or query strings. Do not replace them with guessed names; copy the actual assigned URLs. The `.invalid` defaults are intentional placeholders.

After every change, run `npm run setup:deployment` again. It writes these **private** imports:

| Generated file under `D:\CareLoop\work\deployment` | Destination |
| --- | --- |
| `api.env` | Render API environment variables |
| `ai.env` | Render AI environment variables |
| `frontend.env` | Vercel Production environment variables |
| `n8n.env` | Hosted n8n environment variables |
| `CLOUD-DEMO-ACCOUNTS.txt` | Your fictional cloud login details; keep private |
| `secrets.private.json` | Authoritative cloud secrets; back up privately and never delete/regenerate after storing data |

Import the `.env` files using a platform's **Add from .env** option where available, or add each name/value manually. When entering manually, omit the surrounding double quotes. Never paste the private files into chat, GitHub, issue comments, or build logs. Edit `build/deployment/.env`, not the generated imports; regeneration overwrites the imports. Changing imports locally does not update an already hosted service: re-import changed variables and redeploy that service.

Your hosted database credentials are supplied by Neon/Supabase. Local `POSTGRES_PASSWORD` is not the hosted database password. Generated cloud secrets are separate from your existing local secrets. Existing local encrypted records cannot be copied into the cloud database using different keys; this handover seeds a new synthetic database.

Create an empty **private** GitHub repository, without an autogenerated README. In PowerShell:

```powershell

cd ..

npm run check:github
cd ..
git commit -m "Prepare CareLoop deployment"
git branch -M main
git remote add origin https://github.com/YOUR_USERNAME/careloop.git

```

Replace the GitHub URL. If `origin` already exists, inspect `git remote -v` and use your existing correct remote rather than adding another. No force push is needed. `check:github` examines tracked and eligible untracked files for private paths and known local/cloud secret values; it never stages or pushes. It is not a comprehensive scanner for unrelated third-party secrets or past Git history. Currently the local application and its private work folder are separated by verified ignore rules.

## 4. Create Neon PostgreSQL

1. Create a Neon project and database named `careloop`. PostgreSQL 16 is the version tested locally; choose it if available.
2. Choose a region close to the Render services.
3. In the SQL editor run:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

4. Copy the **direct** PostgreSQL connection URI from Connect into `DATABASE_URL` in `build/deployment/.env`. Use TLS (`sslmode=verify-full` where supported, or the provider's supplied TLS URI). Do not disable certificate verification. URL-encode special password characters when constructing a URI manually.
5. Run `npm run setup:deployment` again. Render's API import now contains the hosted database connection.

The API applies Drizzle migrations and synthetic seeds on startup. Keep one API instance during this demo to avoid competing migrations. The database account needs permission to create the application schema and pgvector extension.

Sources: [Neon connections](https://neon.com/docs/connect/connect-from-any-app), [pgvector](https://neon.com/docs/extensions/pgvector).

**Supabase alternative:** create a dedicated project, enable `vector`, and copy its PostgreSQL URI. On IPv4-only hosting use the Session pooler on port 5432. Retain TLS verification and follow the provider's certificate instructions if needed. CareLoop uses its own authentication; Supabase anon/service-role keys are not used. See [connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres).

## 5. Deploy the AI service on Render

The manual path is easiest for the first deployment because each step produces the next URL. In Render choose **New > Web Service**, connect your GitHub repository, then use:

| Setting | Value |
| --- | --- |
| Name | `careloop-ai` (or your own unique name) |
| Language | Docker |
| Root Directory | `build` |
| Dockerfile Path | `ai/Dockerfile` |
| Docker Build Context | `.` (inside `build`) |
| Health Check Path | `/health` |
| Docker Command | Leave empty; use the Dockerfile command |

Import `work/deployment/ai.env`. Check `AI_MODE=offline`, `PORT=8000`, `OMP_THREAD_LIMIT=1`, and the generated `AI_SERVICE_TOKEN` are present. You do not need provider keys yet. Deploy and wait until healthy.

Open `https://YOUR-AI-HOST/health`. Copy the actual origin to `AI_URL` in the private target file and rerun `npm run setup:deployment`.

Free instances are suitable for testing but may sleep or exhaust resources. If a sleeping service causes a failed extraction, open its health endpoint, wait until ready, then retry the report. For dependable processing choose an always-on plan. See [Docker deployment](https://render.com/docs/docker) and [free-service limitations](https://render.com/docs/free).

## 7. Deploy the frontend on Vercel

Choose **Add New > Project** and import the same GitHub repository:

| Setting | Value |
| --- | --- |
| Framework | Next.js |
| Root Directory | **`build/frontend`** |
| Node.js | **24.x** |
| Include source files outside Root Directory | Enable if shown |
| Install Command | `cd .. && npm ci` (already in `vercel.json`) |
| Build Command | `npm run build` (already in `vercel.json`) |
| Output Directory | Framework default |

Import `work/deployment/frontend.env` into the **Production** environment. Only `API_INTERNAL_URL` and telemetry configuration belong here. No database, AI-service, encryption, or provider keys are browser variables; do not add `NEXT_PUBLIC_` to them.

Deploy. Copy the stable production URL into `FRONTEND_URL`, rerun `npm run setup:deployment`, and update/redeploy the API with the newly generated `CORS_ORIGIN`. Use the exact origin without a trailing slash. Vercel preview URLs are different origins; do not disable the origin check to make every preview work. Use an explicitly configured separate preview environment instead.

Run `npm run check:deployment` locally. Exit code 2 means URLs/provider inputs still need filling or imports need regeneration; it is not a failed application test. A pass checks configuration only, not network connectivity.

Vercel Hobby is for personal/non-commercial use. Its default request-body limit is 4.5 MB, so use synthetic files below 4 MB including upload overhead for the initial demo. The app's local 10 MB limit does not override hosting limits. Larger request bodies have an opt-in paid-plan beta; the default is retained here. Sources: [monorepos](https://vercel.com/docs/monorepos), [Node versions](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions), [Hobby](https://vercel.com/docs/plans/hobby), [function limits](https://vercel.com/docs/functions/limitations).

## 8. Deploy n8n when you want scheduled reminders

Patient reports and clinic queue creation work without n8n, but scheduled inbox notifications require it. In Render choose New > Web Service > Existing Image:

```text
docker.n8n.io/n8nio/n8n:2.48.6
```

Use an always-on plan with enough memory, and attach a persistent disk mounted at **`/home/node`**, initially 1 GB. Persistent disks require a paid service. Use health path `/healthz`. Do not run SQLite-based n8n on ephemeral storage. [Render's n8n instructions](https://render.com/docs/deploy-n8n).

Once Render assigns the URL, enter it as `N8N_URL`, regenerate imports, and import `work/deployment/n8n.env` before final deployment. It sets HTTPS cookies, URL/port/timezone, a stable encryption key, and disables execution-content persistence. `N8N_PROXY_HOPS=1` assumes Render is the only reverse proxy; adjust to your actual topology if adding another proxy. [n8n proxy configuration](https://docs.n8n.io/hosting/configuration/configuration-examples/webhook-url/).

Open the n8n URL and create its separate owner account. Then:

1. Import the four JSON files from `build/automation/workflows`.
2. Create Header Auth credential **CareLoop API automation**: header `Authorization`, value `Bearer ` followed by the cloud API's `AUTOMATION_TOKEN` from `work/deployment/api.env`.
3. In each **Create private inbox notifications** node, select that credential and replace the Docker-only URL with `https://YOUR-API-HOST/api/automation/tick`. Keep each job's existing JSON body.
4. Create Header Auth credential **CareLoop clinic webhook**: header `X-CareLoop-Webhook`, value the cloud `AUTOMATION_WEBHOOK_SECRET`. Select it on **Secured clinic webhook** in the escalation workflow.
5. Run each workflow manually, confirm notification counts and inbox entries, then save and **publish** all four.
6. Run `npm run check:deployment -- --n8n` locally to include the n8n target check.

The local n8n installation is separate; its workflows/credentials are not automatically transferred to the cloud. These exports contain no secrets and begin inactive. Reminders deliver inside CareLoop, not via email/SMS. Schedules require both n8n and the API to remain available. A scheduled polling workflow may keep the API active, consuming free instance hours; do not rely on sleeping tiers for dependable notifications.

## 9. Optional live model and tracing

First complete offline upload tests. Then choose one provider in `build/deployment/.env`:

```dotenv
AI_MODE=live
LLM_PROVIDER=groq
LLM_MODEL=YOUR_AVAILABLE_MODEL_ID
GROQ_API_KEY=YOUR_PRIVATE_KEY
```

For Gemini use `LLM_PROVIDER=gemini` and `GEMINI_API_KEY`. Create a key in [Groq Console](https://console.groq.com/keys) or [Google AI Studio](https://aistudio.google.com/apikey), and choose a currently available model in that provider's account. Regenerate imports, then import/redeploy only the AI service's settings. Do not deploy `host.docker.internal` as a hosted Ollama URL; Ollama needs a separately reachable server and appropriate network access controls.

Optional Langfuse is disabled in the generated import. If enabling later, configure its keys/base URL directly on the AI host and retain that override when reimporting; the generator defaults back to disabled. This implementation sends metadata only. Live model behavior, quotas, and optional tracing still require your own tests with your credentials.
